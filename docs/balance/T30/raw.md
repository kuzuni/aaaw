## 2. 발견 — 실험4 기준① 이 «PLAN 이 적은 기준» 으로 측정된 적이 없다

### 2.1 문면 대 구현

PLAN §7 «T6 제안 합격 기준 — 실험4»:

> ① 어떤 챕터에서도 «**20일(600판)** 연속 실패» 정체가 없을 것

`sim.js` `exp4_gearProgress()`:

```js
const STUCK=parseInt(process.env.EXP4_STUCK||'40',10);          // ← 기본 40일
...
if(tries>GT.runsPerDay*STUCK){ stuckFrom=chap; stuck=tries; break; }   // ← 1200판, 그리고 첫 건에서 break
```

`GT.runsPerDay` = 30 → 엔진 임계는 **1200판(40일)**. PLAN 기준의 **정확히 2배**다.

### 2.2 어쩌다 이렇게 됐나 (기록으로 확인)

`docs/PROGRESS.md:233`(T6 마감, `sess-2221-26307` / 워커 B):

> 실험4 의 «정체 감지» 임계는 20일 → **40일**로 올렸고(`EXP4_STUCK`), 90·300 은 대형 벽이라 걸려도 정상임을 출력에 명시했다.

이유 자체는 옳다 — 같은 줄이 «실험4 도 챕터 90 에서 **621판** 연속 실패로 멈춘다» 고 적고 있고,
90·300 은 주인 확정 대형 벽이라 길게 걸리는 게 정상이다. 문제는 **고친 방식**이다:

| | 해야 했던 것 | 실제로 한 것 |
|---|---|---|
| 벽 챕터(10·15·90·300) | 판정에서 **예외 처리** | 예외 없음 |
| 그 외 챕터 | 임계 600판 **유지** | 임계를 2배(1200판)로 |
| PLAN §7 기준① 문면 | 함께 갱신 | 그대로 20일(600판) |

즉 «벽만 봐주면 되는 문제» 를 **전 챕터의 잣대를 2배로 늘려서** 해결했고, PLAN 문면은 놓쳤다.
T16·T21 과 정확히 같은 실패 모드(«엔진만 고치고 PLAN 을 놓쳤다»)인데, 이번에 어긋난 것은
게임 상수가 아니라 **합격 판정 기준**이라 파급이 다르다.

### 2.3 그 결과 — 세 겹으로 못 본다

1. **600~1200판 정체가 통째로 안 보인다.** 벽이 아닌 챕터에서 20~40일 연속 실패하는 계정은
   엔진 출력에 «정체 감지» 가 찍히지 않는다 → 회차 보고서에 «정체 0 = 기준① 합격» 으로 올라간다.
   T15 가 «챕터 212 에서 1219판» 을 잡을 수 있었던 건 그 정체가 1200판을 **넘겼기 때문**이지
   기준① 으로 걸러서가 아니다(T15 스스로 «기준①(600판) 을 2배 초과 위반» 이라 적었다 —
   기준이 600 인 걸 알면서 1200 짜리 감지기를 쓰고 있었다는 뜻이다).
2. **첫 건에서 `break` 한다.** 기준① 은 «**어떤 챕터에서도**» 라는 전칭 명제인데, 감지기는 첫 정체를
   만나면 루프를 끊어 그 뒤 구간을 아예 돌지 않는다. 정체가 0건인지 5건인지 구별할 수 없다.
3. **끝내 클리어한 정체는 영원히 안 보인다.** `tries` 는 클리어 시 0으로 리셋되고 검사는 하루 끝에만
   돈다 — 800판을 쏟아붓고 뚫은 챕터는 어느 시점에도 임계를 넘긴 적이 «관측되지» 않는다.
   기준① 은 «연속 실패» 를 금지하는 것이지 «끝내 뚫었는가» 를 묻는 게 아니므로 이건 명백한 미탐이다.

## 5. 실측 — 기준① 을 PLAN 문면대로 다시 재면 어떻게 되나
