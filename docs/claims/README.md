# 작업 클레임 (병렬 워커용 lock)

여러 워커가 동시에 돌기 때문에 **작업 단위로 선점**한다. (kkkkkk 규약 이식)

- 파일명: `<작업ID>.lock` (예: `T1.lock`) — 작업ID = `docs/PROGRESS.md` 표의 ID.
- **한 번호는 한 작업만 가리킨다.** 신규 작업은 «이미 쓰인 번호 중 가장 큰 것 +1», 번호 재사용 금지.
- 내용 1줄: `<UTC ISO8601> <SID>` 예) `2026-09-01T21:30:11Z sess-0630-8412`
- 선점 절차: lock 파일 생성 → 커밋 → **push. push 가 먼저 성공한 쪽이 이긴다.**
  push 충돌 시 `git fetch && git rebase origin/main` 후 자기 lock 이 살아있는지 확인 —
  사라졌거나 남의 lock 이 있으면 포기하고 다음 작업으로.
- **90분 지난 lock 은 죽은 것으로 보고 뺏는다** (뺏을 때 기존 파일을 자기 SID 로 덮어 커밋·push).
  장기 세션은 90분 전에 타임스탬프를 갱신해 push 한다.
- 작업이 끝나거나 중단되면 성공·실패 무관 **반드시 삭제**한다.

## ⚠ «직전 슬롯 세션의 lock» 도 남의 lock 이다 (2026-09-03 실사고 2건)

**같은 워커 문자(A~D)라도 SID 가 다르면 다른 세션이고, 그 lock 은 90분 규약을 그대로 적용한다.**
«내 슬롯의 이전 세션이 등재만 하고 끝났겠지» 라는 추정으로 인계하지 말 것 — 앞 세션은 자주 **아직 살아 있다**
(워커는 15분 간격으로 도는데 한 작업은 그보다 오래 걸린다. 밸런스 재적합은 1시간 넘게 걸린 적이 있다).

- 실사고 ①: `sess-1750-40217`(D)가 22분 된 `T106.lock`(`sess-1650-31564`)을 «앞 세션이 끝났다» 며 가져가
  T106 을 통째로 다시 했다. 원 세션은 살아 있었고 lock 을 회수해 스스로 끝냈다(`9315b5d`·`baf0895`).
  **한 시간짜리 재적합 실측이 통째로 버려졌다.**
- 실사고 ②: 같은 날 `T107.lock` 에서 같은 추정으로 인계가 한 번 더 일어났다(`df23fc1`).

**지켜야 할 것**: ⓐ 시각을 계산해 **90분이 실제로 지났는지** 확인한다(lock 파일의 타임스탬프 ↔ `date -u`).
ⓑ 90분 전이면 그 작업은 **건드리지 않고** 다른 작업을 잡거나, 열린 작업이 그것뿐이면 **아무것도 안 하고 물러난다**
(중복 작업은 «아무것도 안 함» 보다 나쁘다 — 남의 결과를 덮어쓸 위험까지 진다).
ⓒ 장기 작업 중인 세션은 규약대로 90분 전에 타임스탬프를 갱신해 push 한다 — 그것이 «살아 있다» 는 유일한 신호다.
